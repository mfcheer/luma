# Still 搜索别名与拼音优化方案（待评审）

日期：2026-10-24。仅完成资料、数据与规则准备；本目录不被应用构建或运行读取，未改动搜索实现、设置、电视安装包或官网。

用户约束：不增加设置项、不要求维护数据、不增加页面说明，保持首页与搜索结果页当前的图标、名称显示和交互。用户仍然在现有搜索框输入，变化仅在更容易找到正确的应用。

## 本轮准备结果

- 68 个产品条目，8 类，200 个独立名称/别名词条；每条已附全拼与首字母。
- 48 个产品的包名与产品对应已有可检查的商店、源码或既有实机证据。
- 9 个条目仍需核对已观察包名与具体产品标签的对应，11 个条目待核实包名。不得把这 20 项称为已完成支持。
- 共记录 60 个准确包名；部分仍为待核实标签条目的观察包，不是 60 个已完成兼容性验证的应用。
- 检出 2 组跨产品完整词冲突：`mgtv` 与 `iqiyi`，保留冲突并明确排序，不悄悄覆盖。
- 8 个名称/别名词条需要音乐读音校正；检查依据为项目当前 TinyPinyin 2.0.3 的真实输出。

数据入口：[完整覆盖表](coverage.md)、[可筛选 CSV](coverage.csv)、[每个词的拼音与简称 CSV](tokens.csv)、[结构化草案](apps.draft.json)、[来源](sources.json)、[撞词报告](review-report.json)。

这些是编辑整理的收录提案；商店或官网证明的产品身份，与我们建议加入的俗称分开记录。包名核实也不代表当前服务仍运营、在用户地区可用，或已经通过所有电视兼容测试。

## 一个输入如何处理

建议使用一份按已安装应用组织的索引，而非让两个搜索结果列表各自排序再拼接。

1. 已有应用目录给出当前可启动应用、真实名称、组件 ID 和首页位置。
2. 从组件取得准确包名，查找内置词库里已审核的对应关系，附加名称/别名/全拼/首字母。
3. 用户输入做现有的全半角、大小写、空格及标点规范化；空输入沿用当前行为。`Netflix`、`Ｎｅｔｆｌｉｘ` 一致。
4. 对每个应用的各个独立词分别匹配，选这个应用最好的那条命中作为排序依据；多命中不叠加分数。
5. 每个当前启动入口只输出一次，再按准确度、同档使用频次、首页顺序稳定排序。

原名称搜索与别名搜索在逻辑上都保留，但只输出一组结果。实现上也可分别召回后合并，只要合并时保留最佳命中、再统一排序，行为应完全一致。一个应用同时命中“网易云音乐”的原名称和“网易云”的别名，只能出现一张卡片，不能因为别名多而排名更靠前。

当前仓库的 AppRepository 已按准确包名选取一个可启动入口，TV 入口优先；搜索层仍以目录中的 `AppEntry.id` 去重和启动，不能以搜索词、应用名称或品牌为去重键。同名的不同包、稳定版与测试版如果同时可启动，分别显示真实图标和原标签，不强行合并。

## 排序提案

排序不采用容易互相抵消的“随意加分”，使用可解释的分档规则。准确度始终优先于使用频次。

| 匹配档位（优先到次要） | 例子 |
|---|---|
| 0. 名称或收录词整词相等 | 原标签“日历”；别名“网易云”；明确简称“yt” |
| 1. 全拼或拼音首字母完整相等 | `jikongjian` / `jkj`；`wyyyy` |
| 2. 名称或普通别名前缀相等 | “网易云”作为“网易云游戏”的开头 |
| 3. 名称或普通别名包含输入 | 输入“播放器”自然命中原名称里含该词的应用 |
| 4. 全拼或首字母前缀相等 | `jikong`，或输入尚未完成的首字母 |
| 5. 原名称全拼或首字母包含输入 | 保留现有搜索兜底能力；新加别名不再做随意的拼音中段扩展 |

同档先区分来源：原标签 > 已审核产品名 > 常用别名/明确简称 > 历史别名。拼音命中再区分全拼 > 首字母。只有以上条件均相同，才比较使用频次；再相同按用户首页顺序，最后以组件 ID 作确定性兜底。

规范化后的英文原名称、全拼和首字母可能完全一样，例如 `youtube`，同一文本只取一次最佳证据。缩写词只做完整相等匹配，不对 `yt`、`nf` 等短缩写做包含或扩展；不为每个英文单词机械生成缩写。

| 输入与假定已安装应用 | 预期顺序 / 边界 |
|---|---|
| “网易云”：网易云音乐、网易云游戏 | 网易云音乐别名完整命中在前；网易云游戏的原名称前缀在后。后者使用更多也不能反超这个准确度档位 |
| “yt”：YouTube、SmartTube | 命中官方 YouTube；SmartTube 不自动继承这个别名 |
| “mgtv”：芒果TV、咪视界 | 芒果TV 的明确 MGTV 简称在前；咪咕TV 产生的拼音首字母命中在后 |
| “iqiyi”：国内、国际两个客户端 | 原标签完整相等者优先；若双方都是同档别名命中，再按使用频次、首页顺序。两张卡片各保留自己的真实名称 |
| “qqyy”：QQ音乐 | 使用审核后的 `qqyinyue` / `qqyy`，不能只依赖库默认 `qqyinle` |
| “播放器”：当贝播放器、其他名称含播放器的应用 | 原名称自然检索仍有效；不人为给所有媒体应用添加“播放器”别名 |
| 只安装未知包、名字也叫“云视听小电视” | 可搜它的真实名称和拼音；不能仅凭显示名称冒用已审核包的 B站 别名 |

这是待实现的排序协议，表中示例目前是验收预期，不是已运行的新搜索结果。

## 使用频次是否值得加

建议加入，但只作为匹配同样准确时的排序依据。它能减少同类、同名、同品牌多个结果的选择成本；若用来压过准确度，用户输入明确应用名却看到另一个常用应用，反而难以理解。

### 记录什么

- 只记录从 Still 首页或搜索结果发起且 `startActivity` 未抛启动异常的应用打开事件。它代表成功提交启动，不声称用户实际观看了多久或应用没有随后崩溃。
- 系统自动进入 Still、开关机、返回桌面、仅选中图标、打开长按菜单均不计数。
- 统一在一个启动入口计数，防止同一次点击在首页、搜索页和公共启动逻辑重复记录。
- 应用频次按准确包名记录，适应应用自身升级后主 Activity 改名；当前目录仍按真实组件 ID 输出。卸载后清理这项本地使用数据，重装从零开始。
- 不读其他桌面或系统的全局使用记录，不申请 Usage Access，不新增权限，不上传搜索或使用数据。

当前 Preferences 未发现使用频次累计字段，因此不能声称已知道用户过去的习惯；新版本只能从加入此能力后开始学习。

### 怎么兼顾“常用”与“最近”

建议用最近使用加权的轻量累计值，旧记录逐渐减弱，而不是无限累加历史总次数。

初始提案：14 天半衰期。每个包只保存 `score` 和上次衰减时间；本次启动先根据经过时间衰减，再加 1。近两周的使用更有影响，长期不用的应用会逐渐让位给新习惯。没有定时任务，读写时懒计算即可。

这个数字是待验证的产品参数，不代表已经测得最优。系统时间倒退不做负衰减或放大分数；大幅前跳最多让旧分数衰减到零，不能干扰准确度。分数损坏、没有记录或所有分数相同时，退回首页顺序即可。

### 保持可预期

- 频次只调整搜索结果同档次序，不改变首页人工排列，也不生成新推荐区。
- 每次进入搜索固定一份频次快照；从结果打开应用再返回，保留当前结果顺序和焦点，不现场跳位。
- 下次重新进入搜索时，新的习惯才参与排序。当前输入改变时，准确度正常重新计算，但使用分数仍取这次会话快照。
- 不统计搜索词历史，不保存逐次启动流水，只需每个包一组聚合数据。
- 新装、很少使用、词库未收录的应用，都继续参与正常名称/拼音搜索；没有使用记录不等于被过滤。

## 数据组织与覆盖原则

`apps.draft.json` 的字段分工：

- `id`：我们维护的产品条目标识，不用于启动应用。
- `bindings`：准确包名、证据类型和来源；不根据包名前缀猜测同品牌客户端。Android 包名保留原有大小写。
- `terms`：独立名称/别名，词类型、匹配方式、规范化文本、全拼、首字母；不拼成一个长字符串，避免跨词边界误命中。
- `identityStatus` / 每个绑定的 `evidence`：明确哪些已有证据、哪些还需核实。发布时逐个绑定审查，不能因为一个产品有某个已核实包就放行它所有待核实变体。
- `excludedAliases`：提醒编辑不要人为加入的泛词/容易误认词。不是运行时黑名单，不能阻止真实名称的自然匹配。
- `lifecycle`：仅记录已查到的官方停运事实；默认 `not_assessed` 表示未评估服务状态，不能解读为仍在运营。
- `review`：全部为待产品评审状态。只有审核通过的绑定和检索词可生成正式词库。

首批范围不限于这台小米电视，包括国内主流影视、音乐/K歌、NAS 与播放器、国际影音、投屏/文件工具、串流游戏、儿童教育及已知设备内置应用。未知应用依旧从系统目录即时发现，不受词库白名单限制。

品牌不等于应用：网易云音乐/网易云游戏、YouTube/SmartTube、Jellyfin/Emby、国内奇异果/国际 iQIYI、Disney+/Hotstar 都不能靠品牌或用途混为一个产品。默认不新增跨产品“相关客户端”召回，本轮仅优化“同一个应用的不同叫法”。

## 拼音处理中的实际问题

现有 TinyPinyin 2.0.3 的逐字默认结果：

| 名称 | 当前库默认 | 审核目标 |
|---|---|---|
| 网易云音乐 | `wangyiyunyinle` / `wyyyl` | `wangyiyunyinyue` / `wyyyy` |
| QQ音乐 | `qqyinle` / `qqyl` | `qqyinyue` / `qqyy` |
| 乐播投屏 | `lebotouping` / `lbtp` | 已正确，保持 |
| 拼音乐园 | `pinyinleyuan` / `pyly` | 已正确，保持 |

不能全局把字串“音乐”的乐一律替换为 yue：在“拼音乐园”里会跨词边界误伤“拼音 / 乐园”。本草案仅对已审核的音乐产品完整词条写入纠正后的全拼和首字母；运行时应通过同一套索引构建流程读取整词纠音，不能把 CSV 当作全局替字规则。

运行时原标签若正好等于已审核词条，使用该词条的正确读音；其他原标签继续由 TinyPinyin 兜底。未收录的多音字产品无法保证读音全正确，这是本轮覆盖的实际边界。

英文和数字保留，不自动把 i/l/1、o/0 相互替换。绿联的 lü 在当前库中用 `lv`；在词条核实阶段可补明确的常见输入形式，不做全局声母/韵母模糊替换。繁体别名也需要逐个审核，不盲目把简繁转换当作产品身份识别。

## 性能与可维护性

- 正式词库随 APK 打包离线发布；用户无需导入、更新词表或配置；我们在应用版本更新中维护。
- 只为已安装且可启动的应用生成索引，不让词库里的 68 个产品自动变成搜索结果，不展示下载建议。
- 在已有应用目录加载/变更时附加一次检索词；查找只扫描内存索引。不在每次按键或从其他应用返回时重新扫描 PackageManager、读图标或请求网络。
- 缓存以目录指纹、标签/语言、词库版本和索引格式版本为依据。应用安装/卸载/升级只更新相关索引；词库升级后后台重建检索部分，不清空已展示的首页和图标。
- 频次是独立的小型聚合数据，不使应用图标缓存失效。写入可异步，不阻塞遥控器操作。
- 不新增大词典、远端接口或搜索框配置；优先复用当前 TinyPinyin 与 AppSearch 架构。
- 将来上线前要用真实 Android 9 和大量应用目录验证索引耗时、首次展示及搜索输入响应。当前没有实施或测得新性能数字。

## 开发前/后的验收清单

1. 数据先校验包名重复、产品标识重复、空词、规范化重复、无来源引用、单字泛别名、跨应用撞词；每个例外有理由。
2. 原有 AppSearchTest 的中英文、全半角、顺序不变、大小写、无结果用例全部继续通过。
3. 增加“网易云”与网易云游戏排序、“油管/yt”、`mgtv` 撞词、`iqiyi` 多客户端、`qqyy` 多音字、拼音乐园不误改、别名命中去重等规则用例。
4. 首次无频次、同档有频次、频次不能越过准确度、只从 Still 启动累计、一次只记一次、启动异常不累计、应用卸载清理、系统时间异常均覆盖。
5. 频次冻结后，从搜索打开应用再返回，结果次序、查询和焦点均不跳动；首页手动顺序始终不受影响。
6. 安装词库以外的应用、应用改名/换语言/升级/换 Activity、损坏或缺失词库时，真实名称和现有拼音兜底仍工作。
7. 视觉回归只确认当前布局没有变化；不增加解释文字、设置开关、别名标签或新首页模块。

本轮仅对草案数据做一致性检查和拼音探测；上述新检索逻辑和频次规则尚未开发、尚未跑应用级验收。
